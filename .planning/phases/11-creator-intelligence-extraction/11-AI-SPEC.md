## 1. System Classification

**System Type:** RAG-backed Structured Extraction (Hybrid)

**Description:**
A server-side TypeScript pipeline that retrieves relevant transcript chunks from Pinecone (RAG), passes them to Claude with a forced tool schema, and extracts a structured creator investment profile — favoured stocks, methodology, sector focus, and preferred index funds. Phase 11 changes this from a single-call category-allocation extraction to a two-call pattern producing two separate layers: a stable 4-month summary and a latest 30-day snapshot. The system is internal-only (no user-facing AI chat); outputs feed the Pulse dashboard as structured JSONB rows in `creator_strategies`.

**Critical Failure Modes:**
1. **Hallucinated tickers** — Claude invents a stock symbol (`AAPL`) for a company the creator mentioned by name but never by ticker. User may buy the wrong stock.
2. **Advice-language in system prompt** — Any occurrence of "recommend", "advise", or "suggest" in the system prompt or output violates the CLAUDE.md constraint and the FCA information-only framing.
3. **Pinecone date filter silently fails** — If the metadata filter syntax is wrong, both stable and latest queries return the same unfiltered chunks. The two layers become identical; the "this month's signals" feature is useless and misleading.
4. **Empty stable profile INSERT** — If Pinecone returns 0 chunks for the 4-month window (creator has no indexed transcripts), the extraction call still fires and Claude produces a zero-confidence output. User sees a profile with no signal.
5. **Allocation column NOT NULL constraint** — `creator_strategies.allocation` must be made nullable in the SQL migration before Phase 11 code can INSERT rows without setting it. Forgetting this migration causes 500 errors on every post-Phase-11 refresh.

## 1b. Domain Context

**Industry Vertical:** Personal Finance — UK ISA Investment

**User Population:** Individual UK retail investors managing their own Stocks & Shares ISA. Single user per instance. Technical sophistication: moderate (can read a table, understands ISA allowance). Investment experience: varies — may be novice.

**Stakes Level:** Medium

**Output Consequence:** The extracted creator profile (favoured stocks, sectors, methodology) feeds directly into what the user sees on their Pulse dashboard. In Phase 12 this data drives the Watch List and share-quantity buy recommendations. A hallucinated ticker or wrong sector could lead the user to research or purchase the wrong security.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|-----------|----------------------|-------------------|--------|--------|
| **Ticker attribution** | Ticker is present only when creator explicitly cited the symbol (e.g., "I hold VWRL") | Ticker inferred from company name ("Vanguard All-World" → "VWRL") without creator stating it | High — wrong ticker = wrong stock |
| **Conviction accuracy** | "high" conviction maps to creator saying "this is my biggest holding / I'm very bullish" | "high" conviction on a passing mention | High |
| **Methodology faithfulness** | 1–3 sentence summary directly reflects creator's stated approach | Generic AI paraphrase ("focuses on long-term value") not grounded in actual creator language | Medium |
| **Recency discrimination** | Latest layer reflects only transcripts from last 30 days; stable layer covers 4 months | Both layers return identical content (date filter failed) | High |
| **No-advice language** | All field values are observational ("creator discusses", "creator expresses") | Any field contains "recommend", "advise", "suggest", "should buy" | Critical — regulatory |
| **Null ticker discipline** | `ticker: null` when creator names a company without citing its symbol | `ticker: "TSLA"` inferred from "Tesla" mention | High — misleads user |

### Known Failure Modes in This Domain

1. **Ticker fabrication**: Claude commonly resolves company names to well-known tickers even without explicit creator citation. Mitigated by explicit tool schema description and system prompt instruction.
2. **Conviction inflation**: Claude tends to score conviction higher than the underlying transcript supports, especially for frequently mentioned names.
3. **Layer conflation**: If Pinecone date filter syntax differs between SDK versions (ISO string vs Unix timestamp), both queries may return the same chunks silently.
4. **Sector over-generalisation**: Claude fills `sector_focus` with generic Technology/Finance buckets rather than reflecting the creator's actual stated emphasis.
5. **Methodology hallucination**: When transcript chunks don't contain methodology language, Claude synthesises plausible-sounding methodology from general knowledge rather than returning a low-confidence empty result.

### Regulatory / Compliance Context

- **FCA (Financial Conduct Advisory)**: Pulse is explicitly an information tool. Any language that could be construed as personalised financial advice violates UK FCA rules. The system prompt must frame all extraction as observation of what the creator *expresses*, never as prescription.
- **GDPR**: Transcript chunks stored in Pinecone are creator-sourced content (public YouTube). User data (holdings, weights) is in Supabase with RLS. No PII is passed to Claude in the extraction call.
- **ISA constraint**: No direct bearing on extraction — but extracted ticker symbols will be used to inform ISA purchases; accuracy is therefore consequential.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| User (ISA investor) | Dataset labeling — verify extracted tickers/conviction against transcripts they've watched |
| Developer | Schema validation, layer discrimination tests, system prompt compliance checks |

## 2. Framework Decision

**Selected Framework:** Direct Anthropic SDK (`@anthropic-ai/sdk`) + Direct Pinecone SDK (`@pinecone-database/pinecone`)

**Version:** `@anthropic-ai/sdk` — already installed (Phase 4). `@pinecone-database/pinecone` — already installed (Phase 3).

**Rationale:**
Phase 11 is an enhancement of an existing, working extraction pipeline (`extractor.ts`), not a greenfield AI build. The pipeline is already implemented as a single async function using direct Anthropic SDK calls with forced `tool_choice`. Adding a framework (LlamaIndex, LangChain) would require a complete rewrite of this function with no material benefit: the extraction logic is simple (retrieve → call → parse → insert), the pipeline has no branching, no state machine, no multi-agent handoffs. Direct SDK also keeps the forced `tool_choice` pattern explicit and visible — abstraction layers sometimes conflict with or hide Anthropic tool_use configuration.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex TypeScript | Strong RAG support, but this is an extraction enhancement, not a new RAG build. Would require adding 15+ packages and rewriting retrieveChunks() for no net improvement. |
| LangChain TypeScript | Abstraction overhead with no benefit for a single well-defined pipeline function. Complexity creep risk. |
| LangGraph TypeScript | Stateful graph orchestration — overkill for a sequential retrieve→extract→insert flow. |
| Claude Agent SDK | Designed for autonomous code-aware agents, not server-side extraction pipelines. MCP-heavy; not the right tool shape. |

**Vendor Lock-In Accepted:** Yes — Anthropic. Project is already committed to `claude-sonnet-4-6` and the Anthropic tool_use pattern since Phase 4. This is a deliberate continuation.

## 3. Framework Quick Reference

> Direct Anthropic SDK patterns for forced tool_use extraction — distilled for this specific use case.

### Installation
```bash
# Already installed — no new packages required

```

### Core Imports
```typescript
import Anthropic from '@anthropic-ai/sdk'
import { getAnthropic } from '@/lib/anthropic/client'
import { embedChunks } from '@/lib/openai/client'
import { getPineconeNamespace } from '@/lib/pinecone/client'
import { createServiceClient } from '@/lib/supabase/service'
```

### Entry Point Pattern (Forced Tool Use — Two-Call)
```typescript
const anthropic = getAnthropic()

// Stable call (4-month window)
const stableResponse = await anthropic.messages.create({
  model: 'claude-sonnet-4-6',
  max_tokens: 2048,
  system: SYSTEM_PROMPT,
  messages: [{ role: 'user', content: stableContextString }],
  tools: [PROFILE_TOOL_DEF],
  tool_choice: { type: 'tool', name: 'extract_creator_profile' },
})

// Latest call (30-day window) — only if chunks exist
const latestResponse = latestChunks.length > 0
  ? await anthropic.messages.create({ ...same config, messages: [{ role: 'user', content: latestContextString }] })
  : null

// Parse forced tool output
const stableBlock = stableResponse.content.find(
  (b): b is Anthropic.ToolUseBlock => b.type === 'tool_use'
)
if (!stableBlock) throw new Error('Claude did not return tool_use block')

const stableProfile = stableBlock.input as CreatorProfile
const latestProfile = latestResponse
  ? (latestResponse.content.find((b): b is Anthropic.ToolUseBlock => b.type === 'tool_use')?.input as CreatorProfile ?? null)
  : null
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `tool_choice: { type: 'tool', name: '...' }` | Forces Claude to call a specific tool; guarantees structured output | Any extraction call — prevents Claude returning prose |
| `Anthropic.ToolUseBlock` | The content block type Claude returns for tool calls | Type guard when parsing `response.content` |
| Pinecone `filter` parameter | Metadata filter applied at query time | Date-range filtering for stable (4-month) and latest (30-day) windows |
| `includeMetadata: true` | Returns stored metadata (title, published_at, text, video_id) with each match | Always required — `text` field is the chunk content |
| `createServiceClient()` | Supabase admin client (bypasses RLS) | All pipeline DB writes — same pattern as Phase 7/8 |

### Common Pitfalls

1. **Pinecone filter syntax**: Date filter uses ISO string comparison. Test with `{ published_at: { $gte: "2025-01-18T00:00:00.000Z" } }` — Pinecone accepts string comparison for ISO dates stored as strings. If `published_at` was stored as a number (Unix ms), use numeric comparison instead. Check existing vectors in Pinecone console before assuming format.
2. **max_tokens must cover the new schema**: The new `extract_creator_profile` schema is significantly larger than `extract_allocation`. Use `max_tokens: 2048` (up from 1024) to avoid truncated tool output on creators with many stocks/sectors.
3. **Empty latest chunks returns null profile, not an error**: If the 30-day query returns 0 results, skip the Claude call entirely (D-09). Do NOT call Claude with an empty context string — it will hallucinate a profile from its training data.
4. **Forced tool_choice on wrong tool name**: If `tool_choice.name` doesn't match the tool `name` in the `tools` array, the API returns a 400 error. Always keep these in sync.
5. **allocation NOT NULL constraint**: Run the SQL migration to add `profile_stable`, `profile_latest` columns AND `ALTER COLUMN allocation DROP NOT NULL` **before** any Phase 11 code path INSERTs a row without `allocation`.

## 4. Implementation Guidance

**Model Configuration:**
- Model: `claude-sonnet-4-6` (existing constant, keep as-is)
- max_tokens: `2048` (increased from 1024 — new schema is larger)
- temperature: default (Anthropic default is 1.0; leave unset for extraction tasks — tool_choice forces structured output regardless)
- No streaming — extraction is a single synchronous pipeline step

**Core Pattern:**
Two-call sequential extraction with Pinecone date filters:
1. Stable call: embed 3 updated query strings → query Pinecone with `published_at >= (now - 4 months)` filter → top 20 unique chunks → Claude call → parse profile
2. Latest call: same queries → Pinecone with `published_at >= (now - 30 days)` filter → if 0 chunks, skip → else Claude call → parse profile
3. INSERT into `creator_strategies`: set `profile_stable`, `profile_latest`, leave `allocation = NULL`

**Tool Use:**
- Single tool: `extract_creator_profile` with the new schema (D-01)
- `tool_choice: { type: 'tool', name: 'extract_creator_profile' }` — forced, same as Phase 4 pattern
- Tool schema must include `nullable: true` annotations on `ticker` fields (D-02, D-03) — use `anyOf: [{ type: 'string' }, { type: 'null' }]` in JSON Schema since Anthropic's tool schema does not support `nullable` keyword directly

**State Management:**
- `refresh_jobs` table tracks step progress — update step labels: `"Extracting stable profile…"` then `"Extracting latest signals…"`
- No in-memory state between the two Claude calls — each is independent
- Stable profile extracted first (D-06); if stable throws, skip latest (fail fast)

**Context Window Strategy:**
- Pinecone returns top 20 unique chunks per window (same as Phase 4 retrieveChunks pattern)
- Each chunk is ~200-400 tokens of transcript text
- 20 chunks × 400 tokens = ~8,000 tokens context — well within Claude's window
- No summarisation or compaction needed at this scale
- `buildContextString()` is unchanged — reuse as-is

## 4b. AI Systems Best Practices

### Structured Outputs with TypeScript Types

```typescript
// Tool input type — mirrors the JSON Schema in TOOL_DEF exactly
interface FavouredStock {
  ticker: string | null   // null when creator named company but not symbol
  name: string
  rationale: string
  conviction: 'high' | 'medium' | 'low'
}

interface SectorFocus {
  sector: string
  stance: 'bullish' | 'neutral' | 'cautious'
  rationale: string
}

interface PreferredIndexFund {
  name: string
  ticker: string | null   // nullable per D-03
  rationale: string
}

interface CreatorProfile {
  methodology: string
  favoured_stocks: FavouredStock[]
  sector_focus: SectorFocus[]
  preferred_index_funds: PreferredIndexFund[]
  confidence: number          // 0-100
  source_video_ids: string[]
}

// Cast tool output (forced tool_choice guarantees type at runtime)
const profile = toolUseBlock.input as CreatorProfile
```

No Pydantic (TypeScript project). Type safety is achieved through the JSON Schema in `TOOL_DEF` input_schema + the TypeScript interface cast. Add a runtime zod validation check in the eval test suite (not production path) to verify schema compliance.

### Async-First Design

The extraction function is `async` and uses `await` throughout — no callbacks, no Promise.all on the two extraction calls (stable must succeed before attempting latest per D-06). The one common mistake in this codebase: `Promise.all` on transcript fetches was explicitly rejected in prior phases (RESEARCH Anti-Pattern T-03-04-05). Keep sequential.

### Prompt Engineering Discipline

**System prompt** (SYSTEM_PROMPT constant): Must be rewritten for the new schema. Rules:
- Never use: "advice", "recommend", "suggest" (CLAUDE.md hard constraint)
- Frame as observation: "You are analysing what this creator expresses/discusses/covers..."
- Explicitly instruct: "Set `ticker` to null if the creator did not cite the stock symbol by name."
- Explicitly instruct: "Set `conviction` based only on the creator's own language — words like 'biggest holding', 'very bullish', 'core position' → high; passing mention → low."
- Keep under 300 tokens — this is a pipeline call, not a conversational context

**User message**: `buildContextString()` output — chunks formatted with Video title, date, ID, text. No changes needed to this builder function.

**Few-shot examples**: Not needed — forced tool_choice with explicit JSON Schema is sufficient for structured extraction. Adding few-shot examples would consume context budget.

### Context Window Management

At 20 chunks × ~400 tokens + system prompt (~300 tokens) + tool schema (~400 tokens) = ~9,100 tokens input per call. Two calls = ~18,200 tokens. Well within `claude-sonnet-4-6` context. No compaction needed.

If Pinecone returns unusually large metadata (long transcript chunks), the `buildContextString` truncation already limits to top 20 — this is the existing Phase 4 pattern and remains correct.

### Cost and Latency Budget

- Per extraction run (1 creator): 2 Claude calls × ~9K input tokens = ~18K input tokens + ~2K output tokens
- At claude-sonnet-4-6 pricing (~$3/MTok input, ~$15/MTok output): ≈ $0.054 + $0.030 = ~$0.084 per creator refresh
- 3 Pinecone queries × 2 windows = 6 vector queries (negligible cost)
- 3 OpenAI embed calls per window (3 query strings) = 6 total = ~$0.0001
- Total per creator refresh: ~$0.08-0.09
- No caching applicable — each refresh intentionally gets fresh extraction
- Sub-task model routing: Not applicable — both calls use claude-sonnet-4-6 (stable and latest use same model, same schema)

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail) | Measurement Approach | Priority |
|-----------|-------------------|---------------------|----------|
| **Schema compliance** | All required fields present; `conviction` is enum; `confidence` is 0-100 integer; arrays are arrays | Code-based: zod validation of tool output | Critical |
| **No-advice language** | System prompt contains none of: "recommend", "advise", "suggest", "should buy", "should invest" | Code-based: string search in SYSTEM_PROMPT constant | Critical |
| **Null ticker discipline** | When transcript chunks contain "Tesla" but not "TSLA", `ticker` is null | Code-based: construct test chunk with company name only, verify null output | Critical |
| **Layer discrimination** | Stable and latest layers return different content when creator has both 4-month and 30-day posts | Code-based: compare two outputs with mocked date-filtered chunk sets | High |
| **Empty latest → null profile** | When 30-day Pinecone query returns 0 chunks, `profile_latest` is null (no Claude call made) | Code-based: mock empty Pinecone response, assert null insert | High |
| **Extraction faithfulness** | Extracted tickers/sectors appear in the source chunk text | LLM judge: pass chunks + profile to Claude judge, ask "Is every extracted item supported by the source text?" | High |
| **Confidence calibration** | `confidence < 50` for creators who spoke vaguely; `confidence > 70` for creators with explicit positions | Human review sample (5 examples per calibration run) | Medium |

### Eval Tooling

**Primary Tool:** Promptfoo (CLI, no infra required) for schema compliance and no-advice checks in CI; manual zod validation script for extraction faithfulness sampling.

**Setup:**
```bash
npm install -D promptfoo
# Create promptfoo.yaml in pulse/ root
```

**CI/CD Integration:**
```bash

npx promptfoo eval --config promptfoo.yaml
```

### Reference Dataset

**Size:** 12 examples (10 minimum per ai-evals.md guidelines + 2 edge cases)

**Composition:**
- 3 examples: Creator with explicit ticker citations ("I hold VWRL") → expect ticker populated
- 3 examples: Creator names companies without tickers ("I like Tesla") → expect ticker null
- 2 examples: Creator with 30-day posts (stable ≠ latest) → expect layer discrimination
- 2 examples: Creator with no posts in last 30 days → expect profile_latest = null
- 1 example: Creator uses investment-adjacent language ("I'd suggest looking at...") → expect methodology captured without reproducing "suggest"
- 1 example: Creator discusses 8+ stocks → expect all captured without hallucination

**Labeling:** Developer labels first pass (verify ticker/conviction against actual transcript text). User reviews conviction labels against creators they follow.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Schema parse failure | `toolUseBlock.input` fails zod validation | Retry Claude call once with explicit "return only valid JSON matching the schema" instruction appended to user message. If retry fails, throw — surface in refresh_jobs.step as "Extraction failed: schema error" |
| Empty context string | `chunks.length === 0` for stable window | Throw immediately — do not call Claude. Surface as "No transcripts indexed — run Refresh first." (same pattern as Phase 4) |
| Empty 30-day chunks | `latestChunks.length === 0` | Skip latest Claude call. Set `profile_latest = null`. Not an error. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Ticker null rate | Monthly: sample 10 recent extractions, check ticker null frequency against creators known to mention tickers | If null rate unexpectedly high → review system prompt clarity, check if conviction instruction is suppressing ticker population |
| Layer discrimination rate | Monthly: for creators with recent posts, compare profile_stable vs profile_latest JSON | If identical → check Pinecone date filter syntax in prod, verify published_at metadata format |
| Average confidence score | Per-run: log confidence from each extraction | If avg confidence consistently > 85 → investigate confidence inflation in system prompt; add explicit calibration instruction |
